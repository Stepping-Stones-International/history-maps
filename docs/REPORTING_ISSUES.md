# Reporting an issue

If something is not working, or you have an idea for improving History Maps,
please open a GitHub issue. An issue is a public ticket that lets the project
team and other contributors understand, discuss, and track a problem or
request.

[← Setup and installation](SETUP_AND_INSTALLATION.md) · [User guide](USER_GUIDE.md)

## Open a ticket

Use the official issue form:

[Open a History Maps issue](https://github.com/Stepping-Stones-International/history-maps/issues/new/choose)

Sign in to GitHub if prompted, choose the issue type, and complete the form as
fully as you can.

## Choose the right type

### Bug report

Use a bug report when something that should work does not work. Examples:

- the application will not start;
- a node or polygon does not save;
- the timeline displays an unexpected result;
- the map does not show a saved layer;
- Docker or the setup instructions produce an error.

### Feature request

Use a feature request for a proposed improvement or new capability. Explain
the problem you are trying to solve and how the change would help users.

### Data or source issue

Use an issue when a historical data pack, citation, coordinate, date, license,
or polygon needs correction. Include the source you consulted and distinguish
documented facts from your own interpretation.

## What to include

For a technical problem, include:

- what you were trying to do;
- the operating system;
- whether you used Docker Desktop, Docker Engine, or a native setup;
- the Docker, Ruby, Node.js, or browser version when relevant;
- the exact command you ran;
- the complete error message;
- the steps needed to reproduce the problem;
- a screenshot or screen recording when it clarifies the issue.

For a map-data issue, also include:

- the topic, node, layer, or pack name;
- the relevant date or date range;
- coordinates or a description of the affected region;
- the source, citation, URL, and license;
- whether the boundary is documented, reconstructed, approximate, or disputed.

## Protect private information

Never include passwords, GitHub tokens, SSH keys, `.env` contents, private
database files, or personal information in an issue. Remove private material
from screenshots and logs before uploading them.

## Using an LLM to prepare an issue

An LLM can help summarize an error and draft an issue. Tell it to preserve the
exact error message and commands, and review the draft yourself before
posting. Do not give the LLM secrets or private data.
